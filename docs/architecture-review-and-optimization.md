# 架构审查与优化结论

本文记录对当前项目架构、数据库与前端状态模型的审查结果，以及 2026-09-01 已确认并实施的优化。详细字段说明见《后端数据库与前端关键数据结构详解》，正式取舍见 ADR-0006。

## 总体评价

项目的主干分层是健康的：Web 只负责交互与 HTTP/SSE，API 管认证和业务事务，Worker 独占耗时模型调用，共享契约不依赖 ORM，PostgreSQL 是权威真相源。它已经具备比普通聊天原型更完整的并发隔离、幂等、恢复和安全边界。

原设计的主要风险不在模块划分，而在分布式边界的最后一公里：数据库终态与 Redis 事件不是同一可靠工作流；限流和 SSE 配额若只在进程内计算会被水平扩容绕过；新对话与首问分两次提交可能留下空对话；无限列表、上下文候选和浏览器终态会随使用时间增长。

## 优点

1. **职责边界明确**：供应商密钥和调用只进入 Worker，API 请求处理器不执行长 LLM 请求。
2. **权威数据清晰**：消息、任务、尝试、用量和审计落 PostgreSQL，Redis 只承担有限保留的实时投影。
3. **并发正确性较强**：用户级事务锁、幂等键、条件状态转换、Writer Token 和 heartbeat 共同防止超额创建、重复提交和双写。
4. **实时恢复设计完整**：用户级 SSE 复用、Generation sequence、专属 Stream、快照和 PostgreSQL checkpoint 能处理重复、缺口与过期。
5. **安全基线可靠**：HttpOnly Cookie、CSRF、刷新令牌轮换、用户作用域查询、日志脱敏和不可信 Markdown 边界均已落实。
6. **可测试性好**：供应商适配器可替换为假实现，API、Worker 和浏览器层都有独立测试入口。

## 原有缺点与处理结果

| 优先级 | 风险                                                                   | 优化结果                                                               |
| ------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| P0     | Worker 提交数据库终态后、发布 Redis 终态前崩溃，页面可能长期停在生成中 | 终态也进入事务 Outbox；稳定事件 ID 去重；`/sync` 用已知任务 ID对账兜底 |
| P0     | Outbox 在持锁事务内等待网络，故障时放大数据库锁竞争                    | 改为短事务领取、事务外投递、短事务确认，增加租约超时、退避和死信       |
| P1     | 队列与认证/事件共用 Redis，队列压力可能影响登录和 SSE                  | 生产拆为 Queue Redis 与 Control/Event Redis；本地允许合并              |
| P1     | 进程内限流和 SSE 计数无法跨 API 实例生效                               | Redis Lua 多维限流与分布式 SSE 租约；控制面故障时安全拒绝              |
| P1     | 刷新令牌重放只拒绝旧令牌，已派生令牌仍可能存活                         | 重放时递归撤销该节点全部后代                                           |
| P1     | “建对话”与“发首问”分两次请求，重试可能留下空对话                       | 新增原子首问接口；浏览器对同一逻辑重试复用操作 ID                      |
| P2     | 列表、上下文和浏览器状态无界增长                                       | 对话游标分页；上下文候选硬上限；终态投影按 30 分钟/100 条清理          |
| P2     | 保留期不清晰，技术表持续增长                                           | 已发布 Outbox、审计和用量分级清理；用户内容及死信不自动删除            |
| P2     | API 与 Worker 配置漂移可能调用错误模型                                 | Worker 在调用前校验 Generation 的 provider/model，不匹配即安全失败     |
| P2     | 只有瞬时 Gauge，无法稳定观察延迟分位数                                 | 增加 HTTP、排队和生成耗时 Histogram，以及 Outbox、对账、租约和僵尸指标 |

## 当前部署边界

```text
浏览器 → Web/API 多实例 → PostgreSQL 单主高可用
                    ├→ Queue Redis → Worker 多实例 → DeepSeek
                    └→ Control/Event Redis → 限流、SSE 租约、事件与快照

API 或独立 Relay → Outbox 领取 → Queue Redis / Control/Event Redis
```

Outbox Relay 暂不建立新的仓库应用目录，而是由 API 包提供独立入口。规模较小时可内嵌 API；需要独立扩缩容时运行 `start:outbox` 并关闭 API 内嵌 Relay。两种模式共享同一领取租约，短期重叠运行也不会重复产生业务事件。

## 明确不做

当前不做多地域部署、Redis Cluster、Event Gateway 单独拆分、多模型注册中心、跨标签对话元数据广播和成本看板。这些能力都会增加一致性协议与运维复杂度，现阶段没有对应业务收益。若流量、供应商数量或容灾目标发生实质变化，应新增 ADR，而不是直接突破当前边界。

## 后续触发条件

- Control Redis 的事件与认证负载互相影响时，再评估进一步拆分 Event Redis；
- Outbox 积压需要独立扩容或 API 发布频繁中断投递时，固定部署独立 Relay；
- 出现第二供应商或同供应商多模型并需灰度路由时，再引入模型目录；
- 明确提出跨地域 RTO/RPO 后，再设计地域复制、故障转移和幂等边界。
